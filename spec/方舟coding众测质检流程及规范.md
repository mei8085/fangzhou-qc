## 一、出题质量：高质量题目判断标准

一句话标准：高经济价值且高评测价值的完整任务。

### 客观标准

| 模块 | 要求 | General Agent | Coding Agent |
| --- | --- | --- | --- |
| 完整性 | 题目完整 | 目标明确；输入、输出清楚；约束条件明确；术语与上下文无关键歧义；不依赖出题人脑中的隐含信息 | 目标明确；输入、输出清楚；约束条件明确；术语与上下文无关键歧义；不依赖出题人脑中的隐含信息 |
| 完整性 | 初始 workspace | 可以为空，但如果有依赖的环境数据必须完整提交 | 提交 workspace，且代码仓库需要至少有 1k+ 行代码（暂定） |
| 完整性 | rubric 完整 | 具有详细清晰的 rubric 和得分点 | 具有详细清晰的 rubric 和得分点 |
| 完整性 | 交付要求完整 | 有明确目标和交付物 | 有明确目标和交付物 |
| 经济价值 | 来源真实 | 背景介绍清晰；可信度高；源自真实业务场景、工单或客户需求；提供真实业务截图，比如数据来源截图、线上系统截图 | 公司项目：代码仓库和公司业务方向描述匹配，且同一个开发者的多条公司任务方向一致，例如同一个开发者不能同时把外贸 SaaS 和酒店管理系统作为公司项目提交。个人项目：初始项目包需要已经能达到上线标准，例如已经部署好后端服务，不接受从零到一或较为简单的个人项目，例如简单的小游戏网页、简陋的桌面 App。学校项目：仅接受研究生及以上的科研项目，不接受本科课程作业项目，例如简单的工程开发。 |
| 经济价值 | 考察能力丰富 | 考核模型的能力点丰富，比如任务规划与拆解、反思与重试、复杂数据库或知识库查询、完成任务所需工具类型丰富多样、SQL 或复杂多表处理、复杂推理与计算等能力。 | 同 General Agent |
| 经济价值 | 任务代表性 | 能代表一类常见或重要工作，而非极偶发的特殊案例；所考能力可以迁移到其他同类任务；避免只考某个内部暗号、冷门配置或偶然知识。 | 能代表一类常见或重要工作，而非极偶发的特殊案例；所考能力可以迁移到其他同类任务；避免只考某个内部暗号、冷门配置或偶然知识。 |
| 评测价值 | 可判定性 | 正确与错误有客观证据；核心得分点可以自动或人工稳定判定；开放题允许多种正确路径，但完成标准必须一致。 | 正确与错误有客观证据；核心得分点可以自动或人工稳定判定；开放题允许多种正确路径，但完成标准必须一致。 |
| 评测价值 | 区分度 | 标准差 > 1.5，且最低分 < 9 分。现有评测机制为 10 分制。 | 标准差 > 1.5，且最低分 < 9 分。现有评测机制为 10 分制。 |
| 评测价值 | 复杂度 | 体现真实任务链路中的多步骤规划、信息获取、工具协作、判断与验证。工具调用轮次可辅助判断复杂度，但不能单独作为高质量依据；若调用主要来自重复操作、无效重试或环境问题，不应计为有效复杂度。参考：模型平均工具调用轮次 > 100，用户交互轮次 > 1。复杂度指标仅作为参考。 | 参考：模型平均工具轮次 > 450。 |

### 正例

```text
任务
某个品牌，请基于某业务看板和导出的订单明细，分析过去 30 天退款率上升的主要原因，并输出一份面向业务负责人的分析结论。
需要包括：
- 退款率整体趋势；
- 按国家、商品类型、渠道拆分；
- 找出异常波动最大的维度；
- 给出 3 条可执行建议；
附上计算口径和关键数据截图。

Rubric
- 数据口径是否正确
- 是否覆盖核心维度
- 是否发现主要异常
- 建议是否可执行
- 结论是否适合业务方阅读。
```

## 二、反馈质量：高质量反馈判断标准

一句话标准：清晰、可复现的任务反馈和模型洞察。

### 客观标准

| 模块 | 要求 | 详细描述 |
| --- | --- | --- |
| 完整性 | 反馈数据完整 | 包含：清晰产物截图或链接、完整任务描述、模型输出结果、关键过程信息；必要上下文材料；能帮助评审人员快速理解问题的补充说明。 |
| 评测价值 | 可复现 | 包含清晰复现路径，其他评审人员无需额外访问即可复现或理解问题：有明确操作步骤；有输入数据或链接；有期望结果和实际结果；问题不是只写“效果不好”“不符合预期”这类主观描述。 |
| 评测价值 | 模型行为洞察深度 | 是否指出具体能力短板；是否能归因到模型行为，而不是环境、权限、数据缺失等外部原因；是否能区分不同模型、框架的表现差异。 |
| 经济价值 | 真实业务影响 | 反馈对应的问题是否会影响真实用户完成任务；是否影响效率、质量、成本、合规或业务结果。 |

## 三、维度二：反馈质量（作业质量）评级表

### 评估对象与要点

- 评估对象：标注人对模型产出结果的打分、备注描述和佐证材料。
- 评估要点：打分是否准确，备注是否规范且言之有据，佐证截图是否支撑其打分结论，trace 执行过程与反馈结论是否一致。

### 评级规则

| 评级 | 判定条件 | 典型场景 |
| --- | --- | --- |
| 高质量 | 打分准确，备注规范，佐证充分，与实际完全一致 | 打分与模型实际产出表现高度吻合；备注格式规范且描述准确；提供了充分的截图或材料佐证；trace 执行过程与反馈结论完全一致。 |
| 合格 | 打分大体合理但存在部分偏差或不完善 | 打分方向正确但与实际存在轻微偏差，例如高估或低估 1 档；备注基本规范但有遗漏；佐证截图覆盖不全面但核心内容有体现；整体判断无严重错误。 |
| 合格 | 打分存在明显问题，备注或佐证质量不达标 | 打分与实际表现有较大偏差；备注过于简略或不规范，无法支撑打分结论；截图缺失或与描述不匹配；存在可发现但未指出的明显问题。 |
| 不合格 | 反馈完全不可信，触发红线规则 | 见下方红线判定规则。 |

## 四、执行口径变化

- 36 期优先按“高质量 / 合格 / 不合格”三档口径判断，不再沿用旧的“高（优秀）/ 中（中等）/ 低（差）/ 不可用（红线）”作为人工判断语言。
- 出题质量的核心从“是不是 coding 场景”升级为同时看完整性、经济价值、评测价值。Coding Agent 题额外强调 workspace、代码仓库体量、真实项目来源和更高工具轮次参考阈值。
- 反馈质量除打分准确性外，新增强调反馈数据完整、复现路径、模型行为洞察深度和真实业务影响。
- 红线类问题仍直接归为不合格；图片中可见的红线补充包括非本人场景和静态展示性页面。
- 飞书列“反馈质量（作业质量）”下拉只有“高质量 / 合格 / 不合格”，命中反馈红线时该列填“不合格”，具体红线类型写到“红线问题”和按模型脏数据标签中，不写“红线”。
- 平台反馈质检中的脏数据标签按 `spec/Coding场景脏数据标签与标准.md` 执行；其中 L1 单条运行记录覆盖反馈质量、平台 & 模型表现、Harness 表现，L2 单任务覆盖题目质量和多模型反馈质量。
